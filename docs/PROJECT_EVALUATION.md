## 一、结论

项目已经从策略脚本升级为生产候选交易内核：持久化订单状态机、UNKNOWN 恢复、私有
WS、交易所托管保护、周期对账、组合硬风控、kill switch、监控备份与研究准入工具已
形成闭环。它可以进入 OKX demo/shadow 的持续验证阶段。

它仍然**不是已获准的无人值守生产系统**。代码能证明故障语义和不变量，不能凭空
证明 OKX 账户权限、真实网络长连、外部告警、异地恢复、策略样本外收益或连续 30 天
无差异。这些是必须在时间和真实基础设施上取得的证据，不是继续加单元测试可以替代。

## 二、本轮已经修复

### 1. 停盘不再阻塞退出

最大回撤停盘现在只禁止增加风险。已有仓位仍会先执行止损/止盈检查，也可以接受
策略 SELL 信号。无仓位时才跳过策略调用，避免停盘期间继续产生无意义的 LLM 成本。

正确的不变量是：

```text
halted + BUY  -> reject
halted + SELL -> allow
halted + SL/TP hit -> allow
```

### 2. 启动改为 fail-closed

首次账户余额、已有持仓或已有持仓价格无法确认时，实盘拒绝启动。运行中如果余额
刷新短暂失败，则继续保留上一份可信快照，不再把网络故障解释为零余额或空持仓。

这样区分了两类情况：

- 启动时没有可信基线：必须停止。
- 运行时已有可信基线但刷新失败：使用旧快照并告警，等待恢复。

### 3. 冻结余额不再被误删

当币种总余额仍足够、但可用余额不足时，系统认为资金可能被未完成订单冻结，保留
风控仓位并进入卖出冷却。只有总余额本身也低于最小交易量时，才清理幽灵仓位。

### 4. 回测现金预算修正

`size_pct` 现在代表包含买入手续费的总现金预算。100% 仓位不会先用完全部现金再
额外扣费，从而避免现货回测中出现负现金和隐式杠杆。

### 5. 回测保护价与成交价对齐

信号在上一根 K 线收盘产生、下一根开盘成交。若存在跳空或买入滑点，止损与止盈会
按照真实入场价同比平移，与实盘逻辑一致。回测结束强平也会计算卖出滑点。

### 6. 配置与工程基线

- `okx.base_url`、`timeout`、`max_retries` 已真正传入 REST 客户端。
- 项目版本统一为 `1.0.0`，补全包描述。
- 增加 GitHub Actions：锁定依赖安装、源码编译和完整测试。
- pytest 开启严格 marker 校验。
- 最初修复将测试由 88 项增加到 100 项；生产内核、故障注入和三路独立审查回归完成后，
  当前本地基线为 455 项通过，故障注入集合为 191 项通过。一键非实盘验收覆盖所有
  测试文件，并将不可替代的真实交易所、时间、基础设施和人工证据显式写入报告。

## 三、初始评估识别的交易安全闭环（现已实现，保留设计论证）

### 1. 订单生命周期不是一次函数调用

原系统的核心假设曾是：

```text
POST 下单成功 -> 收到 ordId -> 认为仓位已经完整成交
```

真实状态机至少是：

```text
intent
  -> submitted
  -> acknowledged
  -> live / partially_filled
  -> filled | canceled | rejected
  -> account reconciled
```

`ordId` 只证明交易所接受了请求，不证明已经按期望数量成交。简单地“多轮查询后超时
就抛异常”也不安全：请求可能已成交，但本地把它当失败并重试，造成重复买入。

推荐设计：

1. 每个交易意图生成持久化的 `clOrdId`，在发送前先写入本地订单日志。
2. 下单响应只把订单推进到 `acknowledged`，不能直接创建最终仓位。
3. 通过私有 WebSocket orders channel 接收状态变化，以 `ordId`/`clOrdId` 去重。
4. REST `GET /api/v5/trade/order` 作为 WebSocket 断线时的补偿查询。
5. 只有累计成交数量变化时才更新仓位，正确处理部分成交。
6. 重启时先对账 pending orders、历史订单、fills 和余额，再允许产生新意图。
7. 对“请求超时但结果未知”使用 `UNKNOWN` 状态，禁止自动重复下单。

OKX 官方说明 orders channel 会推送订单更新，`filled` 是终态；pending 接口只返回
`live` 和 `partially_filled`，已完成订单需要历史或订单详情接口。参见
[OKX API Guide](https://www.okx.com/docs-v5/en/)。

### 2. 保护单必须尽量由交易所托管

原系统止损曾依赖进程定时拉取已完成 K 线后的最新价格。以下任一故障都会产生无保护窗口：

- 进程崩溃或主机重启；
- DNS、代理或 OKX REST 故障；
- 策略线程长时间阻塞；
- API 限速和指数退避；
- 极端行情在两次轮询之间快速穿越止损。

推荐采用“双层保护”：

- 主保护：买入确认后立即提交 OKX conditional/OCO 止损止盈。
- 本地保护：继续保留 PositionMonitor，负责检测保护单缺失、动态收紧和紧急市价退出。

移动止损不能只改本地数值。需要维护 `algoId`，在止损上移时 amend algo order，并
验证修改成功。任何时候都应满足：

```text
有真实仓位 => 有有效交易所保护单，或系统处于明确的 DEGRADED/EMERGENCY 状态
```

OKX 当前提供 `POST /api/v5/trade/order-algo`、algo order details、pending algo
orders 和 amend/cancel 接口，具体字段需以
[官方 Algo Trading 文档](https://www.okx.com/docs-v5/en/#order-book-trading-algo-trading)
为准。

### 3. 建立周期性 reconciliation

本地 `RiskManager` 只是缓存，不应被视为事实来源。交易所才是资金、订单和成交的
最终事实来源。建议每 30–60 秒以及每次重连/重启后执行：

```text
exchange balances
  + open orders
  + algo orders
  + recent fills
        ↓
compare with local order journal + RiskManager + StateStore
        ↓
repair safe differences / halt on ambiguous differences
```

差异处理应显式分类：

- 交易所有仓、本地无仓：恢复并立即检查保护单。
- 本地有仓、交易所无仓：清理前先检查历史订单和成交，不能只看 available。
- 数量不一致：以累计成交和余额为准修正，不假设一次全成。
- 存在未知挂单：冻结该交易对的新信号，直到状态明确。

## 四、回测和量化研究的深层问题

### 1. 单资产结果不能证明组合实盘有效

初始回测对每个 `(strategy, instrument, bar)` 独立执行，而实盘是多个 worker 共享
现金和最大回撤。独立回测无法复现：

- 多个交易对同一时刻争夺现金；
- 高相关币种同时发出买入和止损；
- 组合级最大持仓数与单币种仓位均分；
- 不同交易对成交成本和流动性的差异；
- 某个仓位亏损导致整个账户停盘。

下一步应建立组合事件循环：所有交易对按时间戳合并事件，在同一个现金账户和同一个
RiskManager 上执行。组合回测才应作为实盘配置的最终验收对象。

### 2. 参数敏感性不等于样本外验证

OAT 参数扫描可以发现“参数尖峰”，但仍然在同一段数据上选择和评价模型。反复查看
同一数据集会产生研究者过拟合，即使代码没有未来函数。

建议使用滚动 walk-forward：

```text
训练 12 个月 -> 验证 3 个月
向前滚动 3 个月
只在训练段选择参数
验证段只运行一次，不回头修改
最后汇总所有验证段的连续权益
```

至少同时报告：

- 样本外 Sharpe、Sortino、Calmar；
- 最大回撤持续时间，而不仅是最大深度；
- 与 HODL、现金和简单趋势基准的超额收益；
- turnover、手续费占毛利润比例；
- 不同市场状态下的收益贡献；
- 参数稳定区域，而非单个最优点；
- 多重比较修正或 Deflated Sharpe Ratio。

### 3. 成交成本模型仍偏简单

固定费率和固定滑点适合第一轮筛选，不适合决定真实仓位。现实滑点依赖订单金额、
盘口深度、波动率和时段。建议逐步升级为：

```text
effective_price =
    top_of_book
    + half_spread
    + depth_impact(order_notional)
    + volatility_buffer
```

保守起见，还应对止损跳空、极端价差、流动性突然消失做压力场景，而不是只使用平均
滑点。

### 4. LLM 策略需要单独的评价协议

LLM 信号具有模型版本漂移、非确定性、外部新闻不可重放和费用随时间变化等问题。
传统回测指标不足以证明它有增益。建议将 LLM 定位为受约束的决策组件，而不是最终
事实来源，并记录：

- 完整输入快照、prompt 版本、模型和参数；
- 原始响应、解析结果、风控前后信号；
- token、延迟、错误和降级次数；
- 相对于不使用 LLM 的基线，增量收益是否覆盖调用成本和额外换手；
- 多次重复运行后的决策一致性。

更可靠的实验是 A/B shadow mode：传统策略真实执行，LLM 只记录建议；累计足够样本
后比较“确认、否决、调仓”各动作的边际价值。

## 五、数据、并发与可观测性

### 数据语义

当前行情解析会过滤 `confirm != 1` 的未完成 K 线，这避免了用尚未收盘的数据产生
伪交叉，是正确设计。但 live loop 的 `interval_seconds` 与 bar 边界没有对齐，可能
在同一根已完成 K 线上重复计算。决策日志会去重，但策略内部状态和 LLM 成本仍可能
重复发生。建议以最后已处理 candle timestamp 作为幂等键。

### 并发语义

共享 RiskManager 和 AccountSnapshot 已加锁，买入采用原子预留，这是良好基础。
下一阶段需要把“订单意图预留”也纳入状态机：余额读取、预留、下单、成交和释放必须
围绕同一个持久化 order intent 协调，不能只靠进程内锁。

### 可观测性

日志和终端 dashboard 适合人工观察，但无人值守系统至少还需要：

- 心跳：最后行情、策略、对账和成功下单时间；
- 指标：API 延迟/错误率、连续失败数、订单状态分布、快照年龄；
- 告警：无保护仓位、UNKNOWN 订单、对账不一致、停盘、线程退出；
- 健康检查：liveness 只表示进程存在，readiness 表示行情/账户/订单通道可用；
- 结构化审计日志：每个 order intent 可串联信号、风控、请求、成交和余额变化。

## 六、综合评价中此前缺失的深度讨论

### 1. “有能力”“有证据”“有收益”是三件不同的事

生产评价必须拆成三个正交结论：

| 层次 | 仓库目前能回答什么 | 仍不能回答什么 |
|---|---|---|
| 工程能力 | 超时如何分类、状态如何恢复、何时冻结 BUY、如何退出 | OKX 在真实账户和当前 API 版本下是否完全符合模拟行为 |
| 运行证据 | CI、故障注入、恢复脚本能生成可审计制品 | 告警是否真能触达、空主机是否真能在 30 分钟恢复、30 天是否连续干净 |
| 经济结果 | 回测框架能按共享现金、动态成本和 OOS 口径计算 | 某个策略是否有稳定 edge、容量多大、未来是否继续有效 |

把这三层混在一起是量化项目最常见的评价错误。455 项测试通过只能提高第一层可信度，
不能替代第二层的时间证据，更不能推出第三层的盈利结论。因此仓库默认输出
`NOT ADMITTED` 是设计结果，不是实现失败。

### 2. 故障域不是“程序报错”，而是五类不同事实冲突

需要分别考虑：

1. **交易所故障域**：API 接受但响应丢失、历史窗口延迟、保护单触发后生成新订单；
2. **网络故障域**：REST 可用但 WS 断开、双向分区、DNS/TLS/代理异常；
3. **本机故障域**：进程死亡、磁盘满、数据库只读、时钟漂移、主机丢失；
4. **人员故障域**：重复执行 flatten、错误环境文件、误用 demo/production key；
5. **依赖故障域**：Webhook、对象存储、LLM 或上游行情不可用。

生产内核的原则不是让所有依赖永远可用，而是跨故障域仍保持单调收紧：
`READY → DEGRADED/HALTED/EMERGENCY`，绝不能由后台异常把人工 HALT 自动放宽。
交易所事实有歧义时保留预留并阻止重复风险；外部告警失败时 readiness 也必须失败。

### 3. 策略风险不止最大回撤，还包括容量、拥挤和停用判据

即使样本外指标为正，实盘仍可能因下列原因失效：

- 订单金额增大后冲击成本非线性上升；
- 多个币种在压力期相关性趋近 1，名义分散并不等于风险分散；
- 高频换手的毛收益被 spread、手续费和延迟吃掉；
- 参数平台在历史上连通，但市场制度变化后整体迁移；
- HODL 或简单趋势基准已经解释了绝大部分收益。

所以 canary 不应只规定“最大投入”，还要规定策略级 capacity、成交量占比、最大可接受
滑点、连续多少个 OOS/demo 窗口恶化后停用。放量必须是新的风险审批，不能由近期盈利
自动触发。

### 4. 研究可复现性必须防止“事后构造合格证据”

仅保存最终 Sharpe JSON 不足以审计。有效证据要绑定提交 SHA、配置 hash、账户、
数据/监控来源、生成时间、过期时间、操作人与风险审批人。demo ledger 采用哈希链、
至少 20 小时观测窗口、只能结算当天/前一天且只能顺序追加，避免一秒回填 30 天。

仍应把原始市场数据快照、数据清洗版本、参数搜索空间、失败试验和最终选择理由放入
不可变制品。否则即使没有代码未来函数，也会存在研究者选择偏差和不可复现问题。

### 5. 生产治理的核心是变更控制，而不只是运行时

一次安全发布至少要同时固定：

- 不可变 wheel/sdist 及 SHA-256；
- Git commit、锁文件和配置 hash；
- 数据库 schema 版本及兼容方向；
- OKX API contract 证据；
- canary 账户、时间窗、资金上限和回滚负责人。

风险参数、交易对和策略模型的变化都应视作生产变更。即使代码没变，扩大风险预算也
必须重新审批；数据库通常禁止“恢复旧库覆盖新成交”，只能前滚修复和重新对账。

### 6. 合规、税务与账户条款是仓库外的硬边界

代码无法判断操作者所在司法辖区是否允许自动化交易，也无法替代 OKX 账户条款、
税务记录、数据留存或公司内部授权。生产前必须由实际账户责任人确认适用规则，并把
结论、责任人和有效期作为外部准入证据。这里没有把法律结论写死，正是为了避免代码
对地域和主体作出错误假设。

### 7. SQLite 的边界是部署拓扑，不是文件大小

在单账户、单写者、低频订单下，SQLite WAL + `synchronous=FULL` 是合理选择；引入
PostgreSQL 不会自动解决交易所与本地事实的一致性。真正的迁移触发器是多写者、
自动主备切换、远程服务写入或无法满足异地 RPO。迁移前 repository 契约和事件语义
必须保持不变，否则只是把状态机问题搬到更复杂的数据库。

### 8. “事件存在”不等于“派生投影可重建”

订单、成交和对账调整是事实；`positions` 是为了高效读取而维护的派生投影。只检查
`positions` 当前看起来合理，无法证明崩溃、旧版本 bug 或人工修改后还能恢复。生产
系统需要回答更严格的问题：

```text
position accounting
  == deterministic_reduce(fills + complete reconciliation checkpoints)
```

schema v9 因此让新对账调整保存数量、可用量、平均成本和已实现盈亏的完整检查点，并
提供 dry-run/MAINTENANCE 修复流程。旧 v8 调整只有数量，数学上无法恢复成本和盈亏；
系统明确报告“不完整”并拒绝自动 apply，而不是把零当成事实。这一取舍很重要：可
恢复性首先是信息充分性问题，不是多写一个重算函数就能解决。

启动校验的顺序同样是安全边界：必须先重放既有事实，再允许余额对账写新的完整
checkpoint。否则“数量、均价和 PnL 同时损坏”会先从坏投影生成一个看似完整的新
checkpoint，把腐败状态洗白。当前启动流程在任何余额修复和保护调整前执行 diagnostic；
drift 或旧历史不完整都会保持 DEGRADED，且不会生成新 checkpoint。策略决策的
`strategy_version` 也不再只绑定类名和参数，而同时绑定模块/类源码、信号可执行代码
以及生产 `REVISION` commit，避免同名策略换代码后审计身份不变。

### 9. 原子 BUY 风控能解决 TOCTOU，但不能原子化交易所

余额快照、模式 epoch、持仓槽位、小时意图数、现金预留和 intent 创建现在在同一个
SQLite `BEGIN IMMEDIATE` 内重新验证，消除了两个本地 worker 同时通过旧快照并各自
花掉同一笔现金的 TOCTOU 窗口。

它仍然不是跨 OKX 的分布式事务。数据库提交后、POST 前可能崩溃；POST 到达 OKX 后
响应可能丢失。正确闭环不是尝试“两阶段提交”，而是：

1. 先持久化唯一 `clOrdId` 和预留；
2. 写请求最多发送一次；
3. 歧义结果进入 `UNKNOWN`；
4. 由 WS/REST/成交/余额联合解释；
5. 在确定终态前不释放风险预算。

这说明“原子性”的边界必须写清：本地风险决定可原子，外部副作用只能靠幂等标识和
可恢复状态机收敛。

### 10. SLO 必须来自事件分布，不能来自手工填一个 p99

保护 SLO 的风险不是“没有指标名”，而是统计口径可被人为选择。若操作者直接向
ledger 填 `p99=2s`，签名只证明有人签了这个数字，并不证明它来自全部样本。

当前流程把成交到保护 ACTIVE、启动对账和执行滑点写成 durable system events，再按
UTC 自然日计算 p50/p95/p99/max；运行时与报告器统一使用
`adverse_slippage_ratio`。demo 日锚同时绑定保护/滑点样本数、滑点 p99 和 max、
日报告 SHA-256、S3 对象版本及独立监控公钥指纹。`production_gate record` 会逐项
核对报告与 ledger 参数；硬限比较 max，p99 只作为 SLO，零执行样本不会被伪装成
`p99=0` 的合格滑点证据。

仍需注意统计解释：样本少时 p99 的置信度很低，无成交日也不能证明保护路径健康。
生产评审应同时看样本数、最大值、无保护 watchdog 事件和 30 日累计分布，而不是只看
一个分位数是否低于阈值。低频策略允许某个自然日明确记录零样本，但 30 日准入仍要求
累计至少 30 个真实保护样本和 30 个真实滑点样本；“运行了 30 天”与“观察到足够多
安全路径”因此被分开衡量。

### 11. 账户硬越界与候选订单拒绝是两类风险语义

候选 BUY 因 spread、流动性或预期损失不合格，只应拒绝本次订单；如果当前账户已经
超过仓位名义、总敞口、日损或回撤上限，则事实已经发生，必须锁存 HALTED 并 Page。
两者若都用 `False, reason` 表达，调用者很容易把账户事故当成普通信号落选。

当前实现先评估已实现的账户硬限制，再评估候选市场质量，并把动作区分为：

```text
REJECT_CANDIDATE -> 不创建 intent，READY 可保持
HALT_ACCOUNT     -> 持久 mode epoch + Page，需独立签名恢复
```

这一顺序也避免了“账户已超限，但恰好候选交易对 spread 很宽，于是只返回 spread
错误”的掩盖效应。

### 12. 紧急退出的首要目标是消除敞口，不是保证理想成交

普通 BUY 可以在交易所侧使用已验证的滑点保护；紧急 SELL 面临不同权衡：过严价格
限制可能在暴跌时无法成交，留下更大尾部风险。当前 adapter 不向 SELL 发送尚未由
真实 demo capture 证明支持的 `slippagePct`，退出仍按市价安全优先，同时记录相对
提交基准的真实滑点并触发 Warning。

主动退出的 3 秒目标从获得 exit lease 即开始，由独立定时器 Page。即使 cancel algo
或查询 OKX 的同步调用卡住，告警也不依赖同一个阻塞线程返回。这里必须分别衡量：

- **安全完成时间**：保护取消、余额释放、SELL 提交与终态；
- **告警检测时间**：超过 deadline 后多快形成 durable Page；
- **执行质量**：实际滑点和剩余 dust。

把三者压成一个“退出成功/失败”布尔值，会丢失最重要的尾部信息。

### 13. 研究准入的攻击面包括“删数据”和“自报布尔值”

`covers_full_cycle=true`、`plateau=true` 本身没有证明力。调用方可以删掉亏损日期、
只提交最优参数邻域，或让静态成本 hash 看起来与审批值一致。准入门现在从至少 365
日的 daily benchmark 重算覆盖率、最大缺口和真实日历 90 日牛熊收益，生产者与 Gate
复用同一算法；参数 rows 必须精确覆盖预先批准并签名的 grid manifest，而不是从提交
rows 反推一个更小的“完整网格”。walk-forward 与参数面比较共同的 strategy-family
身份，调度计划和网格评估则分别绑定 evaluation hash，避免比较两个定义天然不同的
hash。生产只接受能够真实构造的 `DynamicCostModel` manifest，连
`fee_rate * stress_multiplier < 1` 都复用模型本身的约束。

数据 provenance v2 把规范化 source artifact 直接纳入签名证据，Gate 重算 source
bytes SHA、dataset hash、行数、时间、交易对和 bar，并从 artifact 的 close 序列与
归一化权重重建 portfolio daily benchmark；只填一个 S3 URI 和自报 SHA 已不足以
准入。独立研究 policy 签名还会在参数评估前预注册 exact S3 URI/version/SHA、参数
grid 和压力场景，阻止看到结果后缩域或把相同 embedded bytes 冒充为另一个对象。
压力证据必须包含批准场景 manifest、逐场景定义/hash、初始/最终资本和损失；Gate
逐行重算最大损失，且至少要求一个 gap≥10%、成交量≤25%、波动≥3x 的硬下限场景。
独立 runner 再对完整 stress evidence SHA 和输入身份签名，离线 Gate 因而不需要相信
操作者手填的 `loss_usdt`。

这仍不能消灭所有研究者自由度。搜索空间为何这样设定、失败实验是否完整保留、数据
供应商是否事后修订，仍需要不可变实验登记和独立研究复核。门禁能阻止显而易见的
合格证构造，却不能替代科研治理。

### 14. 最终信任根不是 JSON，而是身份、密钥和职责分离

即使 evidence JSON 每个字段都正确，如果 operator 同时控制 demo 监控私钥、风险
审批私钥和生产主机 root，系统仍然可以自签“全绿”。有效生产治理至少分离：

- 交易进程身份：只能交易，不能读取备份口令或签署准入；
- 独立监控身份：从不可变运行源生成每日锚；
- 风险审批身份：审核 evidence/ledger/budget 后签准入根；
- root 发布身份：只能在签名有效窗口安装不可变发布并生成 receipt；
- backup 身份：只读数据库、可加密上传，不可交易。

代码已经把公钥指纹、ledger head、evidence SHA、发布 commit/config/account 和预算
绑定起来，但真实密钥托管、轮换、离职回收和应急 break-glass 仍是仓库外控制。生产
评估必须审查“谁能伪造证据”，而不只是“证据格式有没有 hash”。

### 15. 冷恢复的“原子”必须指规范路径始终存在

把旧库先 rename 到备份名、再把候选库 rename 到规范路径，看起来有回滚点，但两个
rename 之间一旦失败，服务读取的规范路径会消失。生产恢复现在先对旧库 checkpoint，
复制并 `fsync` 一份自包含的 durable rollback copy；候选库也 checkpoint、锁存
MAINTENANCE、复验和 `fsync`。真正切换只有一次 `os.replace(candidate, target)`，
失败前旧路径始终存在，成功后新路径立即可见。rollback copy 是事故取证与人工回退
材料，不参与规范路径切换，因此不会扩大不可用窗口。

### 16. Unix 权限与发布证据必须匹配真实进程拓扑

`0600` 对单进程数据库很安全，但与“trader 写、watchdog/backup 独立用户只读”的设计
矛盾。当前生产状态目录固定为 `okxquant-trader:okxquant-data 02750`，数据库为
`0640`；watchdog 和 backup 通过 supplementary group 只读，不能写，交易密钥仍只
对 trader 可见。CI 使用三个真实 UID 验证这些访问关系，而不是只断言 mode 字符串。

同样，生产包由 `git archive` 生成，本来就没有 `.git`。部署 preflight 若现场执行
`git status`，不可变发布会永远失败。现在 CI 在有 Git 元数据的受控构建环境生成故障
证据，绑定 commit、tree 和完整 source+tests manifest，并把 `REVISION` 与证据一起
装入发布包；部署机只验证该证据，不重新发明一个依赖 `.git` 的身份链。

### 17. 最终综合判断

当前项目已经具备**生产候选工程能力**，不再是“补几个异常处理即可实盘”的脚本。
剩余主要风险已经从可直接编码的问题，转移为真实基础设施、长期运行和策略经济证据。
这也是为什么工程评分可以达到 8.5–9 分，而生产准入仍然是零/一门禁中的“未通过”：
成熟度高不等于已经获准承担真实资金风险。

## 七、实施状态与优先级

### P0：真实资金前必须完成（仓库能力已实现，外部证据未签署）

1. 持久化订单意图与 `clOrdId` 幂等。
2. 私有 orders WebSocket + REST 补偿查询。
3. 部分成交和 UNKNOWN 状态。
4. 交易所托管止损/止盈。
5. 启动及周期性 reconciliation。
6. 无保护仓位和订单不一致的即时告警。

### P1：决定策略是否真的有 edge（工具已实现，策略证据未生成）

1. 多币种组合回测。
2. Walk-forward 样本外框架。
3. 动态成交成本和压力测试。
4. 明确基准、turnover 和多重比较修正。
5. 模拟盘连续运行与故障注入。

### P2：工程成熟度（生产模块已落地）

1. Ruff、类型检查和覆盖率门槛。
2. REST/WS contract tests 与可回放的 API fixture。
3. Prometheus/OpenTelemetry 指标和告警。
4. 将文档中的 systemd unit、health check、summary 脚本纳入版本控制。
5. 配置 schema 与启动前完整校验。

## 八、实盘准入标准

建议同时满足以下条件后，才从模拟盘进入受限小资金实盘：

- 连续 30 天模拟盘无未解释的订单/仓位差异；
- 所有仓位在规定时间内拥有交易所保护单；
- 网络断开、进程杀死、部分成交、API 超时等故障注入测试通过；
- walk-forward 样本外扣费后仍有正向风险调整收益；
- 组合最大回撤和压力场景损失在可承受范围；
- 告警能在 1 分钟内触达维护者；
- 单日、单仓、累计亏损均有硬限制，并能人工一键停机和撤单；
- 从交易所导出的成交记录可以与本地审计日志逐笔对上。

在达到这些条件之前，推荐运行模式仍是：

```text
研究回测 -> shadow mode -> OKX 模拟盘 -> 极小资金受限实盘 -> 逐步放量
```
